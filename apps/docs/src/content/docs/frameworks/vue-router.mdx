This package produces an adapter and nothing else. It depends on `@queryweave/core` alone — not on
`@queryweave/vue` — so router synchronization can be adopted without the Vue binding.

## What it owns

- Reading `route.query` and converting it to entries, preserving repeated keys.
- Navigating with `router.push` and `router.replace`, keeping the current path and hash.
- Watching `route.fullPath` and reporting changes, in a scope the adapter owns.
- Reporting a refused or redirected navigation as the transition's outcome instead of throwing.

## What it does not own

Decoding, validation, defaults, and the Vue binding. Those belong to the model and to
[`@queryweave/vue`](/frameworks/vue/).

## Install

```sh
pnpm add @queryweave/core @queryweave/vue-router
```

Vue Router 4.4 and newer, and Vue Router 5, are supported; both are run in the consumer fixtures.

## Example

```ts {8,10-11,13-16}
import { createVueRouterAdapter } from "@queryweave/vue-router";
import { provideQueryAdapter, useQueryModel } from "@queryweave/vue";
import { useRouter } from "vue-router";

import { products } from "./products";

const router = useRouter();
const adapter = createVueRouterAdapter(router);

provideQueryAdapter(adapter);
const filters = useQueryModel(products);

async function showNextPage(): Promise<void> {
  // current route: /products#results, page defaults to 1
  await filters.update({ page: filters.values.page + 1 });
  // /products?page=2#results — the current path and hash are preserved
}
```

Without the Vue binding, drive it directly:

```ts {3-6}
import { createQueryRuntime } from "@queryweave/core";

const runtime = createQueryRuntime({
  model: products,
  adapter: createVueRouterAdapter(router),
});
```

## Handling refused navigation

Router navigation can be declined by a guard or redirected. That is an environment condition, not
a programming error, so the transition resolves with the outcome instead of rejecting:

```ts {1,3-8}
const result = await filters.update({ page: 9 });

if (result.outcome === "refused") {
  console.warn("Query navigation was refused", result.reason); // Vue Router's NavigationFailure
}
if (result.outcome === "redirected") {
  // the router ended on another route; result.snapshot reflects it
}
```

`result.snapshot` is the settled state after the transition whatever its outcome. A guard that
_throws_ is an error rather than a refusal, and it rejects the transition.

<Aside type="caution" title="A refused navigation still resolves the transition">
  `await runtime.update(...)` resolves normally when the router refuses, because the transition did
  what it was asked to do — the environment declined. Read `result.outcome` when a refusal must
  change your control flow.
</Aside>

## Which adapter should you use?

If your application already has Vue Router, use this one rather than
[`@queryweave/browser`](/adapters/browser/). Two writers on one history stack — the router and the
History API — will fight, and the router will not know about writes it did not make.

| Situation                       | Adapter                                          |
| ------------------------------- | ------------------------------------------------ |
| Vue Router present              | `@queryweave/vue-router`                         |
| Vue without a router            | `@queryweave/browser`                            |
| Nuxt                            | [Nuxt](/frameworks/nuxt/) wires this one for you |
| Tests, or no environment at all | `@queryweave/testing`                            |

## Edge cases

- **Path and hash survive** every transition; only the query is rewritten.
- **The router owns the URL's text.** Values are handed over as entries and the router writes them
  in its own encoding and key order, so the bytes can differ from `formatQueryString`; the entries
  do not.
- **A `null` query value** — Vue Router's representation of `?flag` — becomes an empty string entry.
- **Repeated keys** round-trip through the router's array form.
- **A key named after an `Object.prototype` member** (`?constructor=1`) is read and written
  correctly; the router's own parse of it is worked around.
- **Writes wait for `router.isReady()`**, so a transition issued during the initial navigation lands
  on the real route rather than on the placeholder.
- **Notification comes from the route watcher**, not from `push`, because the router already
  reports its own changes. This is why one transition still produces exactly one notification. The
  watcher lives in a detached effect scope owned by the adapter, so it survives the unmounting of
  the component that subscribed first and stops when the last subscriber leaves.
- **After `dispose`**, the watcher stops and later navigation and subscription throw.

## How it is tested

`tests/vue-router/adapter.test.ts` drives a real router through push, replace, refused and
redirected navigation, a subscriber that unmounts before another subscribes, prototype-named keys,
and repeated keys. The `vue-router` and `vue-router-4` consumer fixtures run the packed archive
against a router outside the workspace on both supported majors.
